# 模型与工具测试提示词库

收录可重复使用的提示词，支持项目新增的内容类型：**模型能力测试（`model-capability-test`）**。收到对应提示词或案例编号，并选定模型后，默认直接执行、保存结果，记录测试日期、测试模型和思考强度。模型和思考强度可以来自当前会话的选择，无需在消息中重复。

测试完成后返回结果目录或可运行入口。只有用户另行要求时，才将实测结果整理成 @LeoGuoLabs 的英文推文或文章，并进入项目的内容审核与发布流程。单独要求收录或修改提示词，不触发测试。

## 分类

按产出的主要用途分类，每个案例只设一个主分类；声音、图像、三维等特征作为标签。浏览器内运行的游戏仍归入游戏，具有编辑功能的网页应用归入应用与工具。

分类之外，单独标明呈现形式，例如交互式网页、可运行的桌面应用、视频或静态图。003 和 006 当前明确要求浏览器中的交互式网页；其余原始提示词尚未限定运行平台。

## 使用方法

例如：选好模型和思考强度后，发送“运行 005 照片编辑器”，或直接发送该案例的提示词，即可进入执行与归档流程。

1. 按编号、名称或提示词内容匹配案例。新提示词按现有分类和连续编号收录；本次输入与库内原文不同时，以用户本次提供的原文为准，在运行记录中注明差异，不自动改写库内提示词。将实际输入原样保存为本次运行的 `prompt.txt`。案例说明和观察维度只用于事后记录，不随提示词一起发送，也不添加项目品牌、技术栈或发布要求。
2. 使用用户选定的模型和思考强度，读取可见的当前会话或执行工具设置。记录模型完整名称、可见版本、思考强度原始标签以及配置来源；用户要求与实际设置不同时分开记录。未指定思考强度时沿用当前设置；确认使用默认值但具体档位不可见时记为“默认（具体档位未公开）”，无法读取时记为“未记录”，确认不支持该设置时记为“不适用”。不因缺少可见档位反复追问，也不猜测。选定模型或明确指定的档位不可执行时，保存受阻记录并说明原因，不换模型或档位冒充结果。
3. 创建干净的运行目录，在支持且已获授权时使用独立测试上下文；使用当前会话时，如实记录已有上下文，不宣称独立测试。不为隔离而自行新开用户聊天或委派其他模型。直接执行提示词，保留首次完整回答及全部代码、资源和启动说明，再进行必要的基本检查。后续追问、修复、重试或人工修改均单独记录，保留初始结果。
4. 复制 [测试记录模板](templates/run-record.md) 为本次运行的 `record.md`，填写必填项并保存实际产出。时间使用 **Asia/Singapore**；失败与受阻的尝试也保存记录和错误信息。目录格式见下文。
5. 默认只检查文件是否完整、结果入口是否存在，并在可行时进行基本启动检查；记录实际操作，未做的检查写“未测试”。完成后简短返回结果目录或入口、日期、模型、思考强度和状态。不自动生成推文、配图或演示视频，不打开 X 编辑器，不索取发布确认。

## 结果目录

每个案例下按测试日期、模型与思考强度区分运行：

```text
output/model-tests/<case-id>/<YYYYMMDD-HHMMSS>-<model-slug>-<effort-slug>-r01/
  record.md       # 测试日期、模型、思考强度、状态与结果路径
  prompt.txt      # 本次实际提交的提示词原文
  response.md     # 模型的可见原始回答，也可保留实际原生格式
  artifacts/      # 有代码或其他文件产出时保留，保持可运行目录结构
```

- 例如案例 `005-photo-editor` 的所有模型测试均保存在 `output/model-tests/005-photo-editor/`。时间戳使用测试开始时间；`record.md` 保留带 `+08:00` 的完整时间与时区。
- 目录中的模型与思考强度使用适合文件名的简写；完整名称与原始标签保留在记录中。已确认的默认档位用 `default`，无法读取用 `unknown`，确认不适用用 `not-applicable`。
- 每次独立测试新建目录，必要时递增 `rNN` 避免同秒同配置重名；恢复中断的同一次测试时复用原目录。保留已有目录，不要求迁移旧命名，也不覆盖其他模型的结果。
- 最少保留 `record.md`、`prompt.txt` 和实际回答或产出文件。纯文本测试不必创建空的 `artifacts/`；失败或受阻时注明未产生结果，并保留已有响应或错误，不伪造输出。
- 首次产出保存后再做外部修改，保留初始快照并将修复版本另存。检查日志、真实截图等仅在实际生成时补充，无需为一次简单执行建立完整发布包。

## 后续评估与发布

- 需要比较时，对齐实际提示词、工具权限、运行环境和测试预算；无法对齐的差异明确记录。单次演示只支持对这次结果的判断，不宣称通用排名或模型全面胜出。
- 用户要求整理推文或文章时，再根据选定运行的实测证据撰写英文内容，并按需要获取真实运行截图或录屏。测试执行完成、功能验证通过和内容已发布是不同状态。
- 发布沿用 [项目规则](../AGENTS.md) 的最终内容审核与公开验证要求；执行与归档本身不需要发布确认。

## 新增与维护

- 在 `cases/<category>/<编号>-<short-name>/` 增加案例目录，每个目录至少包含 `README.md` 和 `prompt.txt`，并更新总索引与分类索引。编号全库连续递增，下一条从 `007` 开始，不按分类重新编号。
- 案例说明记录主分类与标签；分类调整时保留案例编号与已有运行记录，更新相关链接。运行记录仍按 `output/model-tests/<case-id>/` 保存。
- 用户提供的测试提示词保持原文，不为补充呈现形式或转成英文而自动改写。编写新的原创提示词或用户明确要求修订时，在简短英文提示词中明确呈现形式，例如 `interactive webpage`、`desktop app`、`video` 或 `image`；案例说明同步标注。保持主题和实现方式的开放性，不扩展成长篇技术要求。
- 每个案例只保留当前 `prompt.txt`，修改时直接覆盖，并同步更新案例说明与索引。提示词库不保留旧版文件、版本号或历史版本记录。
- 案例说明记录测试意图与观察点，实际结果放在各次运行记录中。测试执行后更新该案例 README 的状态，并在“运行记录”处链接对应的 `record.md`；不要用后一次结果覆盖前一次记录。未测项目写“未测试”，未知数据写“未记录”。
- 这里维护提示词与模板；实际测试结果保存在 `output/model-tests/`，用户后续要求的英文发布稿、媒体和发布链接也保存在对应运行目录。常规 Git 提交与同步仍遵循项目规则。
