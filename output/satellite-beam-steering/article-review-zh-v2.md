# 从平面动效到三维卫星科普短片

> 中文审查稿，供核对内容和表达；对应当前英文文章，不作为发布稿。

我第一次用 Codex 制作动效时，讲的是一个金色数据包穿过网络的故事：一条连接中断，备用路径启用，数据包最终到达目的地。用 React 和 SVG 构建画面，再通过 Remotion 渲染，就足以在 24 秒内讲完这个过程。

下一次实验需要换一种画面表达方式。我想说明：当天线面板相对于卫星保持固定时，卫星天线如何改变波束的指向。观众需要先看见实体结构，再进入它的内部，理解相位发生了什么变化，最后带着这个认识回到整颗卫星。

于是有了《Steering without turning》，可以译为《阵面不转，波束转向》。这是一段用 Three.js、React Three Fiber 和 Remotion 制作的 36 秒样片，共六个镜头。这次改进的重点，是把镜头、工作机制和屏幕上的数值联系起来。

## 先看清参考片是怎样讲解的

制作卫星片之前，我分析了一段较长的半导体科普视频。它最有效的手法是反复改变观察尺度：先建立一个完整物体，再进入相关结构，展示结构如何工作，最后拉远，让观众看见它带来的结果。

镜头从手机进入芯片，从灯丝和电极的近景回到完整的电子管。一个器件的输入、内部状态和输出会同时出现在画面中。随后，单个器件又扩展成阵列和更大的系统。镜头始终让观众知道，当前解释的机制发生在什么位置。

这正是上一版路由短片的不足。它的网络拓扑很清楚，运动也可以稳定复现，但大部分解释都停留在同一距离、同一张平面图上。即使增加更多装饰性动画，也无法补上这个缺口。

参考片的分析分为两部分。程序完整解码了 720p 分析副本中的 **12,543 帧**，记录帧间差异、亮度、边缘密度，以及对应音频时间窗的测量值。视觉审查覆盖 **67 个不同的抽样帧**，并在机制变化和转场附近增加采样密度；其中四帧还对照了 1080p 副本。这两组数字对应不同的工作，并不意味着有人逐张看完了 12,543 张静帧。

一个有启发的例子是第 499 帧与第 500 帧之间的切换：画面从密集的芯片表面，进入尺寸更大的内部连线。另一组镜头则把输入波形、器件和输出放在同一个画面里。这两种方式都影响了新片的设计。参考片其他位置出现的大幅亮度跳变，则没有成为卫星片必须模仿的效果。

可以借鉴的方法，是让每次尺度变化都承担解释任务。仅凭这段成片，无法确认作者实际使用了什么软件。

## 让整部短片围绕一条因果链展开

新的制作简报把主题收敛为以下顺序：

> 几何关系变化 → 辐射阵元 → 相对相位 → 主波束方向变化 → 指向地面终端。

36 秒足以解释这一条关系。链路预算、多普勒补偿、调度和切换，可以留给其他短片。

六个镜头各占六秒，也就是在 60 fps 下各占 360 帧：

| 时间 | 镜头与动作 | 观众需要理解的内容 |
|---|---|---|
| 0–6 秒 | 展示卫星、太阳翼和平面天线阵面 | 找到天线在卫星上的位置 |
| 6–12 秒 | 推进到阵面近景 | 识别重复排列的辐射阵元 |
| 12–18 秒 | 分离辐射阵面、馈电层和背板 | 看清经过简化的相位控制结构 |
| 18–24 秒 | 改变八阵元的逐元相位差及其阵列因子 | 将相对相位与波束方向联系起来 |
| 24–30 秒 | 卫星在固定终端上方移动 | 理解电子指向的作用 |
| 30–36 秒 | 回到完整卫星 | 将局部机制重新放回系统中理解 |

分层结构图是一种概念示意，目的是让各层关系可读，并非复现某款商用天线的 CAD 模型。卫星尺寸、移动速度和地面几何关系也都经过示意化处理。

## 根据要解释的内容选择渲染工具

Three.js 提供几何体、材质、灯光和相机。React Three Fiber 把这个三维场景组织成 React 组件。Remotion 负责帧号、视频合成、音频编排和视频渲染。它的 [Three.js 集成](https://www.remotion.dev/docs/three)通过 `ThreeCanvas` 把这些部分连接起来。

这套组合适合短篇技术讲解，因为场景对象和数值计算可以使用同一套代码。相机可以围绕具有三维几何厚度的阵面运动；同一个阵面可以分解成不同层；计算得到的方向图也可以放进同一场景。文字仍然使用 HTML 叠加，相位曲线使用 SVG，从而保持标签清晰、便于修改。

卫星由代码生成的部件组装而成，包括带倒角的本体、辐射贴片、馈电走线、安装细节，以及重复排列的太阳能电池片。在不同镜头中复用同一套几何结构，可以让观众在观察尺度变化时仍然认出这些部件。

画面继续采用暖象牙白、森林绿、少量金色和 Geist 字体。灯光用于帮助识别表面和纵深，不需要依赖深色背景来营造卫星的技术感。

这是针对本项目的选择，并不是对所有动画工具的排名。如果要制作细节更完整的工程卫星模型，或更长、更强调电影质感的片段，建模和渲染需求也会随之变化。

## 让每一帧都能复现

整段视频包含 2,160 帧。每一帧的状态都由请求的帧号推导：

```text
shot = floor(frame / 360)
localTime = (frame - shot × 360) / 60
```

相机位置、缩放、层间分离距离、相位和指向，都是当前镜头局部时间的函数。平滑的变化曲线负责加速和收稳。动画不依赖逐帧累积的状态，因此不会因为之前实际渲染过多少帧而产生不同结果。

这对修改很重要。直接渲染第 1,320 帧，应该与完整导出到这一帧时得到相同的相位状态。它也让我们可以检查某个机制在整个时间区间内的表现，而不必实时播放整段视频。

源码把可复用几何体放在 `Models.tsx`，把时间和公式放在 `motion.ts`，把场景组织放在 `Film.tsx`。因此，修改相机不需要重写天线公式。

## 让数值与画面由同一个状态驱动

核心镜头使用一个理想的等幅八阵元线阵，阵元间距为半波长。八个阵元始终同时工作。波束转向来自它们之间的相对相位变化，不是阵元轮流发射。

本项目的符号约定如下：阵列沿 +x 方向排列，阵面法向为 +z，正扫描角表示从法向朝 +x 方向偏转。采用时间相量 `exp(+iωt)` 和向外传播项 `exp(−ikr)` 时，相邻阵元的馈电相位差为：

```text
Δφ = −2π(d/λ) sin(θ₀)
```

当 `d = λ/2` 时，指向 `+30°` 需要相邻阵元之间具有 `−90°` 的相位差。说明符号约定很重要：改变坐标或相量约定，公式中的正负号可能随之变化，但物理原理不变。

画面中的归一化阵列因子也由同一个扫描角计算：

```text
AF(θ) = |Σ exp(i n k d [sin(θ) − sin(θ₀)])| / N
        n = 0 … N−1
```

相位曲线、相邻相位差读数、波束角读数、波前朝向和主瓣方向，都由这个状态共同驱动。[Analog Devices 的相控阵教程](https://www.analog.com/en/resources/analog-dialogue/articles/phased-array-antenna-patterns-part1.html)解释了相邻阵元的程差关系，也区分了阵元方向图和阵列因子。

数值检查覆盖六秒相位镜头中的每一帧。以 0.1° 步长扫描方向图，得到的最大值方向与设定方向相差不超过 0.05°。另一项检查则逐帧核对跟踪镜头中的指向，确认它与天线到固定终端的连线一致。

这些检查证明的是模型内部一致，并没有验证真实无线链路。方向图保留了旁瓣，但这个窄带模型没有包含阵元方向图、耦合、损耗、极化和波束斜视，也就是波束指向随频率变化的效应。实际阵列还受到扫描范围的限制；[Analog Devices 的第二篇教程](https://www.analog.com/en/resources/analog-dialogue/articles/phased-array-antenna-patterns-part2.html)介绍了其中几项约束。片中可见的波束和被放慢的波前，都是辅助解释的图形。

## 按同一组六个镜头编排声音

原创配乐使用 Python 和 NumPy 合成，采样率为 48 kHz，采用立体声。节拍为 100 BPM，每个六秒镜头正好容纳十拍。一个反复出现的短旋律把各段联系起来，较短的声音提示则对应阵面近景、层间分离、相位变化、跟踪视角和回到全景这些节点。

源 WAV 文件测得的综合响度为 −20.16 LUFS，真峰值为 −5.00 dBTP，为后续母带处理保留了余量。这些是源音频文件的测量值，并非编码后 MP4 的测量值。

这段样片没有旁白。静音观看时，简短字幕和机制画面承担解释任务。合成声音用于组织剪辑节奏，并不是无线电波或太空设备运行声音的录音。

## 修复渲染后才能看见的问题

第一批静帧暴露了两个具体问题。

部分辐射贴片被埋进了带倒角的面板表面。增加亮度无法修复几何问题。把贴片和馈电走线沿局部 z 正方向移出表面，才使它们正确显现。

最初的微距构图还让整颗卫星的太阳翼挡住了标题和侧边说明。这个镜头后来改为专门的阵面近景，同时保留阵面的倾角和重复贴片，让观众能把它与前面的卫星全景联系起来。跟踪镜头也下移了构图，并减小相机放大率，为标题留出空间。

进一步的几何检查发现，地面终端悬浮在球面上方，于是移动球面，让它与终端底座接触。根据三维投影定位的层编号和角度弧线，让标签能够对应到具体结构。扫描角达到精确的 30° 后短暂停留，也让最终的相位读数保持一致。

这些修改都来自对渲染画面的检查。源码正确并不保证构图清楚。先渲染有代表性的静帧，可以在完整导出前，以较低成本发现问题。

## 把导出的文件作为最终交付物

最终检查需要几类证据：用有代表性的全尺寸静帧检查构图，用相邻帧检查运动，用数值检查核对工作机制，再完整解码导出的音视频流。浏览器播放和跳转验证的是另一件事：实际交付文件能否在播放器中正常使用。

最终文件为 1920 × 1080、60 fps，时长 36.000 秒，完整解码得到 2,160 个视频帧。视频采用 H.264、4:2:0 色度采样和有限范围 BT.709 色彩，音频采用 48 kHz 立体声 AAC。对这个 MP4 测得的综合响度为 −18.00 LUFS，真峰值为 −2.86 dBTP。它在浏览器中从头播放至结束，没有报告媒体错误。审片页面也支持逐帧定位。

本机最后一次成功渲染耗时 63.95 秒，母带处理耗时 8.23 秒。这两项时间不包括研究、代码编写、画面审查和修改。

可复现工程把制作简报、源码、可重复生成的配乐、渲染脚本、审查证据和迭代记录保存在一起。在项目目录中，主要步骤如下：

```bash
npm ci
python3 scripts/soundtrack.py
npm run check
npm run stills
npm run render
npm run master
```

Python 步骤需要安装 NumPy。环境还需要兼容的 Node.js，以及 Remotion 使用的浏览器。依赖版本记录在锁文件中。

如果换一个技术主题，我会复用下面这段提示词：

> 围绕一个因果机制制作一段短片。先写制作简报和六镜头分镜：建立完整物体，进入内部结构，展示工作机制，呈现一个受控变量的变化，展示它的结果，最后回到完整物体。根据这些镜头选择渲染工具。用明确的帧时间驱动相机、几何体、标签和声音。数值读数与画面行为应来自同一个模型。尽早渲染静帧，记录具体问题并修改。交付实际视频、可编辑源码，以及已完成检查的证据。区分原理示意模型和实测硬件性能。

下一次改进，仍然可以从这次修改所围绕的问题开始：解释中还有哪一处，需要观众自己想象其中的联系，而画面其实可以直接把它呈现出来？
